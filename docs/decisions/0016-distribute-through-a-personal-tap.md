# ADR-0016 — Distribute through a personal Homebrew tap, as a notarized zip, released locally

- Status: Accepted
- Date: 2026-08-14

## Context

v0.1 is built and green, but the only install path is `git clone && make install` — which asks a
user for a Swift 6 toolchain to get a menu-bar app. "Installable by a stranger" needs three things
the repo did not have: an artefact Gatekeeper will run (Developer ID signature + notarization), a
channel people already use (`brew install`), and a repeatable way to produce both.

Three channel candidates:

1. **`homebrew/cask` (the official repo).** Zero-setup for users (`brew install --cask onair`),
   but its audit gates new casks on project notability — GitHub stars/forks/watchers thresholds a
   brand-new repo cannot meet — and every release PR is reviewed by Homebrew maintainers on their
   schedule, not ours.
2. **A personal tap** (`pmbrull/homebrew-tap`). One extra word for users
   (`brew install --cask pmbrull/tap/onair`), no gate, no third-party review latency, and the cask
   file moves to `homebrew/cask` unchanged if the project ever clears the notability bar.
3. **Direct download** (a zip on the Releases page). No update story at all; every upgrade is a
   manual re-download.

And two ways to produce the artefact:

- **Sign and notarize in CI** on a tag push. Reproducible, but the Developer ID private key must
  be exported into GitHub Actions secrets — a real exfiltration surface for a credential that can
  sign arbitrary code as the maintainer — and the workflow is untestable until a tag fires it.
- **Sign and notarize on the maintainer's machine.** The key never leaves the login keychain;
  every step short of Apple's notary service is testable before tagging (`make dist
  DIST_SIGN_ID=-` exercises the whole lane with an ad-hoc signature). The cost: releases need this
  machine, and the lane is words in a runbook rather than a workflow file.

Measured before deciding: this machine's Command Line Tools ship both `notarytool` and `stapler`
(`/Library/Developer/CommandLineTools/usr/bin/`), so a local release needs no Xcode install. The
keychain currently holds zero codesigning identities, so the runbook starts at certificate
creation, not at signing.

## Decision

- **Channel: a personal tap.** `Casks/onair.rb` in `pmbrull/homebrew-tap`, generated by
  `scripts/make-cask.sh` from the built artefact, pointing at a GitHub Release asset.
- **Artefact: a notarized, stapled zip** of OnAir.app — signed with a Developer ID Application
  identity, hardened runtime, secure timestamp, **no entitlements** (OnAir needs none: no JIT, no
  sandbox, and — invariant A5 — no capture). Zip, not DMG: `ditto -c -k` is scriptable, casks
  consume it natively, and a drag-to-Applications window is ceremony brew performs anyway.
- **Produced locally** by `make release` (dist → notarize → staple → assess), documented in
  `docs/runbooks/release.md`. The signing key stays in the login keychain.
- **Refusal over fallback**: `make dist` fails when no Developer ID identity is present rather
  than shipping an ad-hoc signature that Gatekeeper would reject on every other Mac. The ad-hoc
  path exists only behind an explicit `DIST_SIGN_ID=-` for exercising the lane.

## Consequences

- Users run two commands and get a Gatekeeper-clean app; `brew upgrade` is the update story, so
  OnAir needs no Sparkle, no update checker, no network call it does not already make.
- Releases are single-homed on the maintainer's machine and keychain. Losing the machine means
  re-issuing a certificate, not losing the ability to release — but nobody else can cut a release
  until the CI question is reopened. Acceptable at TEAM = 1; wrong the day there are two.
- The notarization half of the lane is **unmeasured until the first real release** — it needs a
  certificate and a notary profile that do not exist yet. The runbook pins the first release as
  the measurement point, in the same spirit as GAP-0001/GAP-0002: recorded, not glossed.
- A second repo (`homebrew-tap`) enters the release loop; forgetting to update it strands users
  on the old version. `scripts/make-cask.sh` prints the finished file precisely so that step is a
  paste, not a hand-edit.

## Alternatives

- **`homebrew/cask` now** — rejected: the notability audit would bounce a day-old repo; retry
  when the thresholds are met, the cask is drop-in.
- **CI-held signing key** — rejected for now: a key that can sign as the maintainer does not
  belong in repository secrets while one laptop is the whole team. Revisit with a second
  maintainer or an HSM-backed scheme.
- **DMG** — rejected: adds background-image theatre and an extra mount step for zero functional
  gain under brew.
- **Sparkle auto-update** — rejected: a whole update framework (and its XML feed, and its EdDSA
  keys) to duplicate what `brew upgrade` already does for this audience.
